# Database contract

`finanzas_esquema.sql` is the canonical, public schema plus a generic category catalog. It contains no accounts or bank transactions. Initialize a **new** database with `scripts/init_db.py`; do not use a private SQL dump as the schema. The dashboard reads existing files with SQLite `mode=ro` and does not create, import, repair or migrate databases.

An importer is a separate program chosen/generated by each user. It owns all writes and reconciliation. A valid schema alone does not prove that the financial data has been parsed or classified correctly.

## Minimal import mapping

| Table | Required mapping / behavior |
| --- | --- |
| `institutions` | Stable unique `code`, readable `name`; optional country. Banks are not limited to the demo's names. |
| `accounts` | Stable ID, institution, currency (`EUR` or `SEK` for this app), `is_joint` 0/1 and an alias. `iban` and `holder` may remain null; do not require identities to use the app. |
| `transactions` | Stable account link, booking date, original description, signed original-currency amount, currency and unique stable `dedup_hash`. Optional value date, counterparty, balance and provenance. |
| `txn_classification` | One row per parent movement when classified: category link, subcategory and flags. Preserve `method='manual'` on subsequent imports. |
| `txn_splits` | Optional lines, numbered from 1, signed in the parent's currency. Their sum equals the parent amount within 0.005. Each line carries its category and flags; parent classification does not override split flags in the views. |
| `fx_rates` | Dated, positive EUR↔SEK rate with correct base/quote direction and provenance when available. Only real supplied historical rates; no invented samples in a production DB. |
| `balance_snapshots` | Optional reliable account/date/currency balance. Do not infer an opening balance as zero. |

All foreign keys and constraints in the SQL file apply. Optional tables (`budgets`, `documents`, `instruments`, `holding_snapshots`, `recurring_series`, and provenance tables) may be empty. The UI reads available optional records and displays an empty state otherwise. Keep file paths and audit data local.

## Amounts, dates and duplicates

- `booking_date`, `value_date`, snapshot dates and rate dates use `YYYY-MM-DD` (nullable optional dates stay null). Ambiguous source dates require confirmation; do not silently guess month/day order.
- `amount < 0` is outgoing. `transactions.currency` must match the account currency. `original_amount` / `original_currency` can preserve the bank's additional purchase-currency information. Do not replace booked amounts with converted values.
- Keep locale-specific decimals and parentheses/signs correct. A comma decimal is not a thousands separator. Reject invalid numeric values and non-finite amounts.
- Use stable identities across imports. A file hash identifies the original file; a transaction hash identifies a movement. Overlapping exports are not necessarily the same file. Preserve legitimate repeated identical payments and reconcile uncertain matches locally.
- Import in a transaction with `PRAGMA foreign_keys=ON`, using placeholders. Do not use a generic `INSERT OR REPLACE` that can erase classifications or linked rows. Keep a consistent backup before modifying an existing database.

## Classification rules that affect the dashboard

The allowed kinds are `expense`, `income`, `transfer`, `reimbursement`, `investment`, `asset`, `neutral`. Category IDs come from the seeded catalog; look them up by name/kind instead of inventing unrelated IDs. Additional categories can reference a parent and a valid kind. The names `Otros` (unclassified) and `Gastos comunes` (personal contributions to a joint account) have explicit display/reporting behavior; keep these names, using subcategories for additional detail.

- `is_internal_transfer=1` excludes that line from personal cashflow; do not mark ordinary payments or personal contributions to a joint account as internal transfers.
- Positive reimbursement-kind / pass-through lines reduce spending and do not become income. Outgoing advances remain spending until reimbursed.
- `is_one_off=1` puts a qualifying outgoing expense in the separate one-off metric. **The canonical monthly view already removes these from `expenses` and `net_expenses`.** Do not subtract them twice.
- `investment` and `asset` flows do not become expenses. Their monthly indicators are signed net outflows: a redemption reduces the value, and a net withdrawal can produce a negative indicator.
- Accounts with `is_joint=1` only appear in the joint view. Personal transfers categorised `Gastos comunes` count as the user's own household contribution; do not add the joint account's purchases again.

The canonical income expression counts eligible positive non-internal lines, not just categories of kind `income`; importers must identify refunds, reimbursement and transfers accurately to avoid misreporting them. Uncertain rows should be shown for review, not assigned a confident invented meaning.

## Views are the interface

| View | Use |
| --- | --- |
| `v_all_lines` | Canonical expansion: one unsplit row or one row per split. |
| `v_transactions` | Personal account lines only. Count parent movements with `COUNT(DISTINCT id)`. |
| `v_monthly_cashflow` | Authoritative monthly native-currency income, reimbursements, habitual expenses/net expenses, one-offs, invested and assets. |
| `v_joint_transactions` | Joint account lines only. |
| `v_split_errors` | Any returned row means the split sum does not match its parent. |

Do not change views to accommodate incorrect exports. For consolidated EUR/SEK, the app distributes the authoritative monthly values across transaction dates, checks that these weights reconcile, and converts using the latest rate on/before each date. An absent previous rate is an error, not permission to use a future rate. For single-currency source data, rates are still needed if the user selects the other display currency. Supply rates covering the earliest relevant movement or snapshot.

## Validate and publish data locally

```bash
python3 scripts/validate_db.py --db data/finanzas.db
```

The validator reads the file in `mode=ro`, checks canonical tables/views, integrity/foreign keys, dates, currencies, numeric values, classification flags, split consistency, and EUR/SEK rate coverage. It reports counts and issues, never transactions, names, IBANs or passwords. A missing FX dataset fails validation even if a same-currency dashboard would work: either supply the real dataset before using both display currencies or explicitly keep that limitation in your own workflow.

Also reconcile against the actual bank statement: source row counts, signed totals by account/month/currency, balances when supplied, rejected rows, and reimport/overlap behavior. The validator cannot determine account ownership, whether a category is meaningful, or whether an apparently repeated payment is a duplicate. Review those separately.

For monthly publication, finish the import transaction or publish a consistent SQLite backup, then refresh the dashboard. If using WAL, preserve readable sidecars or publish a consistent checkpointed copy using the writing tool. The dashboard never performs the checkpoint. See the deployment notes in the README.
